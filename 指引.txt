## 三、构造确定性整数循环测试

使用以下程序作为核心实例：

    void test(int p, int x) {
        while ((p == 0 && 0 <= x && x <= 2) ||
               (p == 1 && 3 <= x && x <= 4)) {
            x = 4 - x;
            p = 1 - p;
        }
    }

其中 p 和 x 是任意整数输入，初始值不得固定成仅一个循环状态。

如果官方前端不直接支持这个 C 函数形式，请按照真实支持的格式转换为等价的单循环模型，并验证转换前后的语义一致。

数学整数语义为：

G(p,x) = (p=0 ∧ 0≤x≤2) ∨ (p=1 ∧ 3≤x≤4)

T(p,x,p',x') = (p'=1-p) ∧ (x'=4-x)

必须确认循环体仅在 G 成立时执行、转移为确定性且相关状态下不存在整数溢出；若使用 LLVM 或 C 整数语义，记录具体类型及求解器解释方式。

固定初始 Recurrent Set：

R0 = (p=0 ∧ x=0) ∨ (p=1 ∧ x=4)

目标联合泛化集合：

R* = (p=0 ∧ 0≤x≤1) ∨ (p=1 ∧ 3≤x≤4)

R0 包含循环：

(0,0) → (1,4) → (0,0)

R* 还包含：

(0,1) → (1,3) → (0,1)

但状态 (0,2) 不是非终止状态，因为其后继为 (1,2)，已经不满足 guard。

因此，直接把整个循环条件 G 当作 Recurrent Set 是错误的。

## 四、首先进行独立 SMT 语义验证

在接入官方 RSG 之前，编写一个独立的 SMT 检查器，使用数学整数语义验证：

- R0 非空，并包含可到达的循环状态；
- R0 ⇒ G；
- R0 ∧ T ⇒ R0'；
- R0 ⇒ R*；
- R* ⇒ G；
- R* ∧ T ⇒ R*'；
- R* 严格大于 R0。

SMT 检查必须覆盖所有整数状态，而不只是枚举一个有限范围。

还要明确验证两个单项候选：

A = (p=0 ∧ 0≤x≤1) ∨ (p=1 ∧ x=4)

B = (p=0 ∧ x=0) ∨ (p=1 ∧ 3≤x≤4)

预期 A 因 (0,1) → (1,3) 而违反归纳闭包；B 因 (1,3) → (0,1) 而违反归纳闭包；R* 通过检查。

进一步检查，本程序在任意整数入口状态上的精确非终止集合是否等于 R*。这可以通过 guard 内的有限相位分类和符号验证完成。

还需要设置至少三个负面测试，例如包含 (0,2) 的候选、不包含种子状态的候选，以及违反闭包的候选，以检查验证器能否正确拒绝。

输出每项 SMT 检查的 SAT、UNSAT 或 UNKNOWN 结果、反例以及查询耗时。UNKNOWN 不得解释为成功。

## 五、实验 A：真实运行原始 CondTerm RSG

A3：反复调用原始 RSG，直到语义不再扩展或达到预先设定的安全上限。

## 六、实验 B：最小双项联合泛化

不要立即实现完整的 Global MaxSAT 框架。

本轮只实现一个极小且可审计的双项联合搜索原型，用来验证协调泛化的能力差别。

冻结与实验 A 相同的 R0、谓词语言和候选边界，仅引入两个布尔选择：

- s1：是否将第一项的 x 上界从 0 放宽到 1；
- s2：是否将第二项的 x 下界从 4 放宽到 3。

枚举四种完整赋值：

(0,0)、(1,0)、(0,1)、(1,1)。

对每种候选分别检查包含性、循环条件和归纳闭包，记录结果及反例。

注意：这些选择变量必须全部赋真或假，不能把未选变量留成自由变量后，以 UNSAT Core 的结论替代完整候选的检查。

验证联合候选是否可达到 R*，并通过独立 SMT 检查。

该原型应命名为 `Joint-2-Selector` 或同等明确名称。它只是验证能力的最小见证，不是通用 MaxSAT 算法，也不能将手工指定目标 R* 的验证时间误报为自动搜索的运行时间。

同时实现一个极简单的备选基线，例如枚举固定候选区域后进行闭包修复，用来判断这种小规模现象是否确实需要优化求解器。

如实际存在可行的自动联合搜索，再考虑后续扩展成 SAT/MaxSAT-CEGIS；本轮不要求完成该框架。

## 七、实验 C：比较实际收益

重点比较三个层面。

**第一层：泛化能力。**

比较 A1、A2、A3、A4、A5 和 Joint-2-Selector 的最终集合。

使用 SMT 证明集合的包含关系与严格扩展关系，不允许仅根据字符串长度或采样数量判断。

在有限展示区域 p∈{0,1}、x∈{0,1,2,3,4} 内，R0 应覆盖 2 个状态，R* 应覆盖 4 个状态。但这种局部数量只能用于直观说明，不能代替全整数语义证明。

**第二层：泛化成本。**

比较原始 RSG 和自动联合搜索的墙钟时间、SMT 次数、求解时间、峰值内存。

对时间很短的测试，先进行预热，再至少重复 30 次，报告中位数、波动范围和异常值。保存环境和随机种子。

如果联合方法更慢，不得只报告集合扩大而忽略时间成本。

**第三层：对 CondTerm 整体流程的潜在价值。**

在不注入固定 R0 的情况下，先对测试程序运行一次原始 CondTerm，记录 RSLearn 实际生成的种子和最终结果。

然后尝试两个单独实验配置：

- 冻结 R0，并使用原始 RSG；
- 冻结 R0，并将经验证的 R* 作为 oracle 泛化结果。

如果官方架构允许，比较后续循环迭代次数、ddlTerm/RSLearn 调用次数、求解器耗时和整体运行时间。

必须明确：注入 R* 的版本属于 oracle 上界测试，不能代表实际联合搜索算法的端到端加速。

如果工具已经在正常运行时学到 R*，也必须记录这一事实；它说明本例未必构成端到端性能问题。

若有时间，再构造少量结构相似的变化实例，改变变量名称、析取项顺序、常量平移等，检查结果是否稳定，但不能用大量高度相似的合成例子夸大统计证据。

- `GO`：真实官方接口表现出受限能力差别，且联合搜索能以可接受成本解决，值得扩大真实实例审计。

- `NO-GO`：官方实现或合理的强基线已经解决该现象，原先设想的能力缺口不成立。
- `BLOCKED`：无法获得或正常执行官方实现，证据不足。
