# 下一阶段实验指引：CondTerm 自然 RSG 输入的协调泛化困难实例挖掘与算法比较

## 一、你的任务与研究目标

你现在是一名从事 SAT/SMT 求解、程序分析、终止性与非终止性验证的研究工程师。

请在现有服务器 `/root/RSG` 上，基于已经完成的第一阶段实验，继续开展第二阶段研究。你需要实际阅读代码、修改程序、运行实验、验证结果，并提交全部源代码、测试脚本、原始日志和中文研究报告。

**本轮不要直接实现完整 Global MaxSAT + Incremental SMT。**

我们的研究目标不是证明 MaxSAT 一定有效，而是先通过实验回答：

**RQ1：在官方 CondTerm 的自然运行过程中，协调泛化能力缺口是否真实存在，出现频率有多高？**

**RQ2：如果存在这类困难实例，简单闭包修复、强化逐项泛化与联合搜索分别能解决多少？哪些情况必须进行多个 DNF 析取项的协调修改？**

**RQ3：找到更大的 Recurrent Set 后，是否有可能减少 CondTerm 的外层迭代和总体求解时间，还是泛化成本抵消了收益？**

本阶段的重点是发现具有研究价值的真实困难实例、隔离不同算法的能力差异，并判断下一阶段最值得开发哪种算法。

请直接执行实验，不要仅提供实验设计方案。

而 standalone RSLearn 又能够直接学到 R*。

这些现象说明，必须同时考虑种子语法、数据共享流程、泛化算法和外层求解成本。

## 五、第三项工作：实现可公平比较的强化基线

请基于冻结输入构建统一的 RSG 离线测试框架。

对于任意候选 R'，至少检查：

`R0 => R'`

`R' => G`

`R' ∧ T => R''`

这里最后一个公式表示转移后仍属于 R'，不是任意程序状态的无条件转移。

若原程序存在额外路径条件、验证假设或状态变量，必须使用官方 VC 的正确语义，而不是错误地简化成只有两个整数变量的示例。

对于未知、超时或无法证明的候选，一律不得视为有效。

所有算法均在相同原始 R0、相同程序语义和明确记录的候选语言下比较。

### Baseline A：官方原始 RSG

使用未修改的 `modifiedGeneralizeRS_2`。

这是最主要的能力基线。

### Baseline B：重复逐项 RSG

反复运行官方逐项泛化，直到集合语义不再改变，或者达到预先设定的资源限制。

不要仅通过公式文本相同判断语义等价，应使用 SMT 或安全的等价性判定。

如果重复逐项就能解决问题，不能将它归类为必须协调修改的实例。

### Baseline C：强化单项泛化

在有限候选模板下，允许一次只修改一个 DNF 析取项，但对该项使用比官方启发式更充分的候选搜索。

候选操作可以包括已有谓词的删除、常量放宽和允许的区间删除。

必须保留输入中真实存在的混合谓词，例如 `p+x`、`p-x` 及其他可用属性。

不要把所有自然输入强制简化成 unary 矩形。

对于候选空间较小的实例进行完整穷举。对于空间过大的实例，使用明确的候选预算，并报告搜索不完备性。

该基线用于区分“官方启发式漏解”与“单项修改在当前候选语言中本来就无法扩展”。

### Baseline D：简单闭包修复

这是本轮必须认真比较的强基线。

先复用已有的 `Closure-Repair`，但必须保留它原本的适用条件。

当循环 guard 被严格证明为有限状态集合且规模可控时，可以进行精确有限状态闭包计算。

**不能在无限状态循环上截断整数范围，然后声称获得了精确 Recurrent Set。**

对于无限状态循环，尝试实现一个受限的符号闭包版本。

可以基于已有谓词构造有限符号区域，使用 SMT 判断区域是否满足 guard、后继是否包含在当前区域集合中，并通过反例删除或必要的区域细化寻找闭合集合。

必须保证算法返回的每个结果都经过独立完整 SMT 检查。

如果符号区域划分过粗、不能表达种子或候选集合，允许进行有预算的细化；无法继续时应返回 `unsupported` 或 `unknown`，不能声称闭包方法已被证明失败。

尽可能区分精确有限闭包、符号闭包、带预算的抽象闭包等实现配置，避免将不同能力混为一谈。

这一部分很重要：如果简单符号闭包已经能够有效解决大部分困难实例，下一阶段可能应该研究增量闭包传播，而非 MaxSAT。

### Baseline E：自动发现的双项联合泛化

将已有 `Joint-2-Selector` 从手工指定两个位置的演示程序，扩展成一个受限但真正自动工作的算法。

对于某个冻结自然输入：

首先解析 DNF 和现有谓词，生成有限的候选删除、放宽或区间选择操作。

然后自动寻找需要联合修改的两个析取项，而不是预先告诉算法哪两个项需要改变。

在预算允许的范围内搜索所有相关候选组合，并使用 SMT 验证完整 R'。

对于闭包反例 `s → t`，应允许通过覆盖后继 t 修复候选，而不是一律把 s 当作负例排除。

可采用穷举、约束反馈或轻量 SAT 搜索，但暂不需要引入完整 MaxSAT 优化器。

优化目标优先是发现合法的严格扩展，之后才考虑覆盖代理指标或公式复杂度。

### Baseline F：小规模多项联合搜索

只有在双项搜索发现真实协调依赖、但仍留下明显未解决的候选时，再考虑将联合项数扩展到 3 或 4。

必须设置候选数量、SMT 调用和时间预算。

不要求无条件进行指数规模穷举。

这一配置的目的在于观察真实困难实例的协调宽度，而不是尽可能消耗求解资源。

## 六、第四项工作：自动识别真正的协调泛化困难实例

对每个冻结 RSG 输入，比较上述方法返回的结果。

对于任意两个集合 A 和 B，使用 SMT 检查：

`A => B`

`B => A`

如果 A 被 B 包含且存在 `B ∧ ¬A` 的模型，才可以称 B 为 A 的严格扩展。

若两者互不包含，应报告为不可比较，不能仅根据一个采样覆盖数量宣称某一方法更优。

重点搜索以下类型：

**Type I：官方 RSG 未扩展，但强化单项方法可以扩展。**

这说明主要问题可能是原始泛化启发式不充分，而不是必须修改多个析取项。

**Type II：单项方法在固定候选语言内无法扩展，但简单闭包可以找到更大的集合。**

这支持协调泛化确实有用，但不支持必须使用 MaxSAT。

**Type III：单项方法和简单闭包方法都无法在给定预算或表示条件下有效得到扩展，而双项或多项联合搜索能够找到有效严格扩展。**

这是本轮最值得进一步分析的困难实例。

必须区分简单闭包的超时、不可支持、候选语言不足与已经证明无法扩展。超时不能被报告为算法能力不可能。

**Type IV：联合方法扩大了集合，但搜索成本过高，或者新增状态对外层终止条件推断没有帮助。**

这说明存在能力收益，但缺乏实用性能收益。

对于可能属于 Type III 的实例，必须保存完整输入、候选语言、独立 SMT 证明、反例、算法运行轨迹和成本数据。

对于声称“任意单项泛化都失败”的实例，必须给出固定候选语言内的完备搜索证据或数学证明。有限预算搜索未发现扩展，只能称为未发现，而不能称为不存在。

优先分析来自不同程序、具有不同状态结构的实例，而不是大量常量平移或变量重命名形成的重复样本。

## 七、第五项工作：研究协调依赖结构和规模问题

如果自然 RSG 输入中确实出现有效的协调泛化实例，请进一步分析这些实例的结构。

尝试从闭包反例中建立候选区域之间的依赖关系。

例如，某个新增状态属于区域 A，其后继需要区域 B 才能覆盖；区域 B 的新增状态又可能要求区域 C 一同扩展。

但必须注意，一个后继状态可能由多个不同的区域覆盖，不能在没有证明的情况下把可选关系变成强制依赖。

对典型实例记录 DNF 项数、原子谓词数、候选操作数、联合修改的最小已证实范围、SMT 反例数量以及实际求解成本。

如果自然实例不足以观察规模趋势，可以在冻结自然实例的结构基础上构造少量有明确用途的合成压力测试，增加区域数量或依赖宽度。

合成测试必须与真实程序结果分开报告。

特别关注以下问题：

简单闭包修复是否因为符号区域数量迅速膨胀而变慢？

逐项搜索是否停在一个无合法单项改进、但存在联合改进的局部状态？

双项联合搜索是否随候选数量增长迅速变慢？

能否利用 SMT 反例提前排除不可能的联合候选，减少完整验证次数？

此阶段可以提出依赖感知搜索的初步方案，但只有实验发现真实瓶颈后，才考虑进一步开发复杂算法。

## 八、第六项工作：有条件开展 CondTerm 端到端实验

不得手工注入目标 R* 并将其称为实际新算法。

至少比较原始 CondTerm、CondTerm + 简单闭包修复、CondTerm + 自动联合泛化（如果该方法已实现）。

所有配置必须使用相同的原始程序、模型配置、随机种子、学习器、终止证明器与外层停止规则。

对每种配置记录：

端到端成功率、最终终止条件、外层迭代次数、RSLearn 入口调用次数、终止侧调用次数、RSG 时间、SMT 求解成本、进程总时间和峰值内存。

不能只统计泛化阶段节省了多少时间，还要测量泛化自身新增的搜索成本。

注意，上一阶段官方 RSG 在 Mono/C# 中执行，而联合与闭包原型位于 Python 环境。两种独立进程的微基准并不具备完全相同的计时边界。

因此，最终性能比较必须优先使用实际集成后的完整 CondTerm 运行。

对选中的实例采用成对、随机轮转的重复测试。先运行 3 次预热，再尽可能完成 20–30 次正式测量，并报告中位数、离散程度与成对差值置信区间。

同时检查最终条件是否正确。对于能够证明精确条件的实例，应验证新旧输出在相关程序语义下的等价性。

如果发现较大 Recurrent Set 反而增加后续证明难度，也应完整记录。

如果没有自然实例支持集成，不要为了完成性能表而进行不必要的系统改造，直接报告机制阶段的结果并停止。

## 十、建议的停止规则

这一轮是困难实例发现与研究路线筛选，不需要无休止扩充实验。

完成官方自然输入语料采集和核心基线比较后，按照以下情况决定是否继续深入：

**GO：** 在多个不同的真实程序上发现经过独立 SMT 验证的协调泛化收益，且联合方法在闭包、强化单项等强基线面前仍有能力或效率优势。尤其是可以证明简单闭包算法存在实际瓶颈时，值得进入依赖感知 SAT/MaxSAT 搜索研究。

**PIVOT：** 自然实例中确实存在大量协调泛化机会，但符号闭包修复能以更低成本解决。此时建议转向符号闭包、增量前驱传播或闭包反例复用。

**NO-GO：** 真实程序中很少出现这种缺口，或者获得更大的 Recurrent Set 后仍无合理的整体收益预期。此时应停止这一特定技术路线，避免为了维持 MaxSAT 设想而继续构造特例。

**PARTIAL：** 自然输入上有正面信号，但覆盖范围、完备性、性能或集成证据不足。

**BLOCKED：** 官方实现、数据提取或关键验证无法正常执行，必须记录具体障碍。

如果没有证据支持强结论，应保留不确定性，不能人为提升判断等级。
